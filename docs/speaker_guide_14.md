## 2. 김태완(팀장) · 데이터 파이프라인

**맡은 부분:** 시작과 끝, 공공데이터를 받아 회사와 위치로 잇는 과정(`pipeline/`).

### 1 표지 (약 45초)

> 안녕하세요. 다닐만한가 팀입니다. 다닐만한가는 "이 회사, 다닐 만한가?"라는 질문에 국민연금, DART, 서울시 전월세 같은 공공데이터 숫자로 답하는 구직자용 웹 서비스입니다. 저 김태완이 데이터 파이프라인, 서승범이 프론트엔드, 양준석이 DB와 SQL, 최진영이 백엔드와 운영을 맡아 10월 2일부터 21일까지 만들었고, 지금 보이는 주소와 QR 코드로 바로 써 보실 수 있습니다. 오늘은 프로젝트 소개, 기획과 요구사항, 아키텍처와 DB 설계, 핵심 기능 구현, 시연, 문제 해결과 회고 순서로 말씀드리겠습니다.

### 2 기획 배경 · 문제 · 주요 사용자 (약 1분 5초)

> 구직자가 회사를 판단할 때 보는 정보는 대부분 채용공고와 익명 리뷰입니다. 하나는 회사가 쓴 글이고, 하나는 한 사람의 경험입니다. 그런데 객관적인 근거가 될 공식 데이터는 이미 공개되어 있습니다. 국민연금공단은 사업장마다 가입자 수, 입사·퇴사 인원, 고지금액을 매달 공개하고, DART에는 재무제표가, 서울시에는 신고된 전월세 계약이 있습니다. 문제는 그대로는 쓸 수 없다는 점입니다. 한 달치 스냅샷이라 추이를 보려면 여러 달을 쌓아야 하고, 사업장 단위라 회사로 묶어야 하고, 출처 사이에 공통 키가 없고, 주소에는 건물번호가 없고, 실거래는 지번 단위입니다. 이 간극을 메우는 것이 이번 프로젝트였습니다. 주요 사용자는 신입이나 이직을 준비하는 구직자, 특히 지방에서 서울이나 판교로 오는 구직자입니다. 이 회사가 성장하는지, 사람이 자주 떠나는지, 근처에서 살 수 있는지를 한 번에 알고 싶은 사람들입니다.

**넘기는 말:** "기능과 화면 설계는 프론트엔드를 맡은 서승범이 설명드리겠습니다."

### 8 공공데이터 잇기: 데이터 · 매칭 · 좌표 (약 1분 10초)

(최진영에게서 받음)

> 핵심 기능의 바탕은 서로 다른 공공데이터를 잇는 일입니다. 데이터는 다섯 가지입니다. 국민연금 사업장 13개월, 회사 13만 7천 곳, DART 법인과 재무, 서울시와 국토부 전월세 계약 47만 건, 역 326곳, 그리고 주소정보누리집의 건물과 출입구 좌표입니다. 파일마다 인코딩과 열 형식이 달라 하나로 맞췄습니다. 출처 사이에는 공통 키가 없어서 회사는 사업자번호 앞 6자리와 정규화한 이름으로 DART와 연결합니다. 둘 다 같으면 정확 연결, 같은 6자리 안에서 이름 유사도가 85점 이상이면 유사 연결이고, 그 외는 억지로 잇지 않습니다. 가입자 1,000명 이상 회사의 79%가 연결됩니다. 지도 좌표는 국민연금 주소에 건물번호가 없어서 DART 본사 주소, 상호 검색, 도로 중심, 동 중심의 네 단계로 정했습니다. 처음엔 좌표 API를 2만 6천 번 부르려 했는데 4시간 반이 걸릴 것으로 보여, 주소 출입구 파일로 직접 계산해 16초로 줄였습니다.

**넘기는 말:** "이은 데이터로 숫자를 계산하는 핵심 SQL은 양준석이 설명드리겠습니다."

### 13 부족한 점과 향후 개선 (약 50초)

(양준석에게서 받음)

> 마지막으로 한계와 다음 할 일입니다. 추정 연봉은 회사 평균의 하한이고 개인이나 직무별 연봉이 아닙니다. 서울과 성남 사업장만 다루고, 국민연금 공개 기준 미만인 작은 회사는 없습니다. 회사 위치는 약 1만 3천 곳만 건물 단위이고 나머지는 대략 위치로 표시합니다. 채용공고는 모으지 않고 검색으로 연결합니다. 다음으로는 지금 수동인 월 갱신을 명령 하나로 묶고, 성남에 썼던 방식 그대로 경기 다른 시로 넓히고, API 서버를 미국 서부에서 아시아 리전으로 옮겨 응답 시간을 줄이려 합니다. 이 프로젝트에서 배운 것은 공공데이터가 "있다"와 "쓸 수 있다" 사이가 멀다는 점이고, 그 사이를 SQL과 검증 숫자로 메웠습니다. 감사합니다. 질문 받겠습니다.

### 14 질의응답 · 추가 시연 (약 20초)

> 들어 주셔서 감사합니다. 질문 받겠습니다. 화면의 QR 코드로 지금 바로 서비스를 써 보실 수 있습니다. 시간이 있으면 역 세 곳 비교와 24개월 시세 추이, 계산식과 한계를 정리한 계산 방법 페이지, DART 재무, API 문서 화면도 추가로 보여 드리겠습니다.

## 3. 서승범 · 프론트엔드

**맡은 부분:** 요구사항 · 화면 설계와 시연(`web/`). 질의응답 때 추가 시연도 맡는다.

### 3 기능 요구사항과 화면 설계 (약 55초)

(김태완에게서 받음)

> 기능 요구사항과 화면 설계입니다. 요구사항은 61개를 P0부터 P3까지 우선순위로 나눴고, 그중 50개를 구현했습니다. 4개는 방식을 바꾸거나 일부만 했습니다. 지도 핀 팝업 대신 왼쪽 상세 패널을 쓰고, 월 자동 갱신 대신 사람이 확인하는 수동 갱신으로 바꾼 것 등입니다. 하지 않은 7개는 모두 채용공고 연계입니다. 사람인과 고용24가 개인에게 채용 API를 주지 않고 크롤링은 하지 않기로 해서, 사람인과 잡코리아 검색 바로가기로 대신했습니다. 반드시 필요한 P0는 모두 구현했습니다. 주요 기능은 회사 검색, 회사 상세의 세 가지 지표와 업종 백분위, 지도, 회사와 역 비교, 근처 주거비, 채용 바로가기입니다. 그리고 모든 화면에 기준월과 출처, 추정치의 한계를 함께 보여 주는 것도 요구사항으로 정했습니다. 화면은 지도를 첫 화면으로 정했습니다. 위쪽 검색 막대와 지도는 그대로 두고, 왼쪽 패널만 목록, 상세, 비교로 바뀌어서 회사를 주변 회사와 함께 보면서 이동할 수 있습니다.

**넘기는 말:** "이 화면을 받치는 전체 구조는 백엔드와 운영을 맡은 최진영이 설명드리겠습니다."

### 10 시연 (약 3분)

(양준석에게서 받음)

> 이제 실제 화면으로 보여 드리겠습니다. (브라우저로 전환) 첫 화면은 지도입니다. 위쪽에서 핀에 표시할 지표를 증감, 퇴사율, 연봉으로 바꿔 보고, 왼쪽 목록을 10곳씩 또는 20곳씩 페이지로 볼 수 있는 것을 보여 드립니다. 다음으로 우아한형제들을 검색해 상세를 엽니다. 결과표의 숫자를 보고, 아래로 내려 근처 역 세 곳의 원룸 시세와 월급 대비 부담률, 사람인과 잡코리아 바로가기를 보여 드립니다. 비교에 세 회사를 담아 가입자 지수 그래프를 보고, 지역을 관악구로 바꿔 신림역 시세를 엽니다. 반경을 500미터에서 750미터로 바꾸면 지도의 원과 시세가 함께 바뀝니다. 이어서 역 세 곳을 담아 역 비교를 열고, 지역을 성남시 분당구로 바꿔 판교역 시세와 네이버의 근처 주거비를 보여 드립니다. 판교의 IT 회사도 서울 회사와 같은 기준으로 볼 수 있습니다. 끝으로 점선 핀 하나를 눌러 대략 위치 안내를 보여 드립니다. 인터넷이 안 되면 로컬 서버나 미리 녹화한 영상으로 대신합니다.

- 시연 순서와 화면에 나올 값은 [demo.md](./demo.md) 2장을 따른다. 화면이 안 뜨거나 느리면 3장(비상 계획)대로 로컬 서버 → 녹화 영상 순으로 바꾼다.
- 우아한형제들은 업종 분류가 없는 회사라 업종 비교 판정이 나오지 않는다. 그 안내 문장을 가리키며 "업종이 섞인 분포와는 비교하지 않는다"고 한마디 덧붙인다.
- 시연이 끝나면 슬라이드로 돌아온다.

**넘기는 말:** "만들면서 부딪힌 문제는 최진영이 말씀드리겠습니다."

## 4. 최진영 · 백엔드와 운영

**맡은 부분:** 시스템 구성 · 기술 스택 · API(`app/`), 배포와 운영, 오류 해결 사례.

### 4 전체 시스템 구성도 (약 1분)

(서승범에게서 받음)

> 전체 시스템 구성입니다. 위쪽은 로컬, 아래쪽은 배포 환경입니다. 로컬에서는 한 달에 한 번 공공데이터 파일과 API를 파이썬 배치로 받아 품질 검사를 거쳐 MariaDB에 적재하고, raw에서 core, mart까지 만듭니다. 결과를 사람이 확인한 뒤에만 덤프나 필요한 표를 배포 DB에 올립니다. 배포는 세 부분입니다. Vercel이 Next.js 화면 파일을 내려주고, 브라우저는 그 화면에서 Railway의 FastAPI를 직접 불러 JSON을 받습니다. API는 같은 Railway 안의 MariaDB와 사설망으로만 연결되어 DB 포트는 밖에 열려 있지 않습니다. 배포 DB에는 API가 읽는 mart와 작은 조회 표만 있고, 전월세 원본이나 계약 같은 큰 표는 로컬에만 둡니다. 그래서 배포 서버는 읽기만 하고, 데이터를 바꾸는 일은 모두 로컬에서 합니다.

### 5 기술 스택 (약 1분 20초)

> 기술 스택입니다. 수집과 정제는 파이썬 3.12로, httpx와 pandas를 썼습니다. 공공데이터 API는 재시도와 하루 호출 한도를 두고 부릅니다. 회사명 매칭은 rapidfuzz 유사도, 좌표 변환은 pyproj로 했고, 좌표는 이용 조건에 맞게 주소정보누리집에서 얻은 것만 저장합니다. 가운데에 있는 DB가 핵심입니다. MariaDB 11.4에서 윈도 함수, 백분위, 공간 인덱스, 월 파티션을 썼고 스키마는 Alembic 마이그레이션 11개로 관리했습니다. API는 FastAPI와 SQLAlchemy로, 통계 SQL 파일을 그대로 실행하는 읽기 전용 서버입니다. 화면은 Next.js 15와 React, 그래프는 Recharts, 지도는 네이버 지도를 썼고, API 타입은 OpenAPI 문서에서 자동으로 만듭니다. 테스트는 pytest와 Playwright, CI는 GitHub Actions이고 배포는 Railway와 Vercel입니다. 일부러 쓰지 않은 것도 있습니다. LLM이나 임베딩 없이 통계는 모두 SQL로 계산했고, 채용 사이트는 크롤링하지 않았습니다.

**넘기는 말:** "데이터를 담는 테이블 구조는 DB와 SQL을 맡은 양준석이 설명드리겠습니다."

### 7 API 요청 · 응답 흐름 (약 1분 25초)

(양준석에게서 받음)

> API 요청과 응답 흐름입니다. 회사 상세를 예로 들겠습니다. 브라우저가 회사 상세 주소로 GET 요청을 보내면, 먼저 미들웨어가 CORS를 확인합니다. 우리 웹 도메인의 GET만 허용하고, 브라우저가 갖고 있는 ETag가 지금 응답과 같으면 본문 없이 304로 끝냅니다. 라우터는 경로와 쿼리 값을 검증해서 형식이 틀리면 422, 없는 회사면 404를 돌려줍니다. repository는 sql 폴더의 SQL 파일을 그대로 실행하는데, 값은 모두 바인딩 파라미터로 넘깁니다. DB에서는 refresh_mart로 미리 집계해 둔 mart 행만 읽습니다. 돌아오는 길에는 service가 표본 부족, 대략 위치 같은 flags와 주거비 부담률을 만들고, Pydantic 응답 스키마가 모양을 검증합니다. 이 스키마는 OpenAPI 문서가 되고, 웹은 거기서 타입을 자동으로 만듭니다. 마지막으로 캐시 미들웨어가 ETag와 1시간 캐시 헤더를 붙여 JSON을 내보내고, 화면은 숫자와 함께 flags를 안내 문장으로 보여 줍니다. 모든 응답에 기준월 as_of가 들어갑니다. 요청할 때 집계를 하지 않기 때문에 로컬 부하 측정에서 상세 8밀리초, 검색 6밀리초였습니다.

**넘기는 말:** "그 데이터를 어떻게 만들었는지, 공공데이터를 잇는 과정은 김태완이 말씀드리겠습니다."

### 11 오류와 해결 사례 (약 55초)

(서승범에게서 받음)

> 만들면서 부딪힌 문제 중 여섯 가지입니다. MariaDB는 CHAR 원본의 생성 컬럼을 오류 1901로 거부해서 VARCHAR로 바꿨습니다. 공간 조인은 앞에서 말씀드린 대로 쌍을 먼저 만들어 풀었고, 750미터를 더했을 때는 임시 테이블 한도 문제를 만났습니다. 회사와 역 순위를 모든 사업장으로 매기면 같은 역이 겹쳐 1순위가 사라지는 버그가 있어서 회사마다 대표 좌표 하나로만 매기게 했습니다. 좌표 API는 몰아서 부르면 오류를 정상 응답처럼 돌려줘서 실패로 캐시되는 문제가 있었고, 결국 API 대신 주소 파일로 계산했습니다. 전각 괄호로 쓴 주식회사 표기가 정규화되지 않아 같은 회사가 둘로 나뉜 문제도 있었습니다. 이런 문제는 모두 증상, 원인, 해결, 재발 방지를 문서로 남겼고 지금 34건입니다.

**넘기는 말:** "프로젝트 성과는 양준석이 정리하겠습니다."

## 5. 양준석 · DB와 SQL

**맡은 부분:** ERD와 테이블 관계, 통계 SQL(`migrations/` · `sql/` · `tests/sql/`), 성과 정리.

### 6 ERD와 테이블 관계 (약 1분 20초)

(최진영에게서 받음)

> 테이블 관계입니다. 가운데 있는 company가 기준입니다. 국민연금에는 사업장 단위로 나오기 때문에 company 아래에 workplace, 그 아래에 월별 스냅샷 workplace_monthly가 붙습니다. 회사는 사업자번호 앞 6자리와 정규화한 이름으로 하나를 정합니다. 위쪽 주황색은 DART입니다. company_dart_link가 회사 하나와 DART 법인 하나를 잇고, 연결 방식과 점수를 함께 저장합니다. 오른쪽 파란 mart_company 표가 화면에 나오는 요약과 월별 지표이고, 업종과 시군구 이름은 작은 조회 표에서 붙입니다. 아래쪽 청록색은 역과 전월세입니다. 회사마다 가까운 역 세 곳을 company_station에 미리 계산해 두고, 역별 시세와 24개월 추이는 mart_station 표에 둡니다. 역과 건물은 외래키가 아니라 좌표로 잇는 관계라 점선으로 그렸습니다. 반경 500미터와 750미터 공간 조인으로 묶습니다. 전환율과 보험료율 같은 기준값은 코드 상수가 아니라 표에 두었고, raw 표는 원본을 받은 그대로 보존합니다.

**넘기는 말:** "이 표들을 화면까지 꺼내는 API 흐름은 다시 최진영이 말씀드리겠습니다."

### 9 핵심 SQL (약 1분 15초)

(김태완에게서 받음)

> 핵심 SQL 세 가지입니다. 통계는 모두 SQL로, 데이터를 갱신할 때 미리 계산해 둡니다. 첫째는 빠진 달 처리입니다. 퇴사율은 이번 달 상실자를 직전 달 가입자로 나누는데, 어떤 회사가 한 달 자료에서 빠지면 LAG 윈도 함수가 두 달 전 값을 가져와 틀린 비율을 만듭니다. 그래서 앞 행이 정말 직전 달인지 PERIOD_ADD로 확인하고, 아니면 NULL로 둡니다. 둘째는 업종 안 백분위입니다. 회사의 60.7%가 가입자 10명 미만이라 한두 명만 나가도 퇴사율이 크게 흔들립니다. 그래서 표본이 부족하거나 업종 분류가 없는 회사는 윈도 파티션을 따로 나눠 정상 회사의 분포에 섞이지 않게 하고, 그 회사들의 백분위는 NULL로 둡니다. 셋째는 역세권 공간 조인입니다. 역에서 500미터, 750미터 안 건물의 계약으로 시세를 내는데, 공간 조인을 백분위 윈도 함수와 한 쿼리에 넣었더니 MariaDB가 공간 인덱스를 쓰지 않아 기간 하나에 5분이 걸렸습니다. 역과 건물 쌍을 먼저 임시 테이블로 만들고 그 쌍으로 계산하자 0.9초가 됐습니다.

**넘기는 말:** "이제 실제 화면은 서승범이 보여 드리겠습니다."

### 12 프로젝트 성과 (약 1분)

(최진영에게서 받음)

> 성과는 숫자로 정리했습니다. 먼저 정확도입니다. 인원은 대기업 다섯 곳을 DART 직원 수와 대조해 ±6% 안에서 맞았습니다. 연봉은 국민연금 소득 상한 때문에 항상 낮게 나와서 화면에는 하한 추정으로만 표시합니다. 성능은 요청 때 집계하지 않는 구조 덕분에 로컬 부하 측정에서 상세 8밀리초, 검색 6밀리초로 목표인 300밀리초와 500밀리초를 크게 넘었고, 화면은 한글 글꼴을 미리 받던 것을 줄여 상세 화면 Lighthouse 성능이 53점에서 81점이 됐습니다. 규모는 서울과 성남 회사 13만 7천 곳, 역 326곳, 전월세 계약 47만 건입니다. 품질은 pytest 234개와 화면 테스트 15개를 PR마다 CI가 돌리고, 모든 변경을 PR 120개 넘게 리뷰해 병합했습니다. 결정은 10건, 부딪힌 문제는 34건을 문서로 남겼습니다.

**넘기는 말:** "부족한 점과 앞으로의 계획은 팀장 김태완이 말씀드리겠습니다."
